# Security Policy

This software is actively maintained (by the community). An important part of the maintenance is to check for security vulnerabilities, and patch these as soon as applicable. 
It is however not possible to guarantee the support for every version as the software evolves. As such you will find a table under [Supported Versions](#supported-versions) to see which versions are actively maintained.

You are encouraged to share any (possible) vulnerabilities you have found, via the appropriate routes, see [Reporting a Vulnerability](#reporting-a-vulnerability).

## Supported Versions

Please note that this overview will update for each new version. Due to limitations in collaborators it's impossible to guarantee a period of support per version.
System administrators are encouraged to regularly upgrade to the latest (stable) version.

| Version | Supported          |
| ------- | ------------------ |
| 1.x_stable   | ✔️ |
| 1.x_unstable   | ✔️ |
| <1.x_stable   | ✔️ |
| <1.x_unstable   | ✔️ |

Legend:
| Mark | Meaning |
| -------- | ---------------- |
| ✔️ | (almost) fully supported |
| ➖ | limited support |
| ❌ | no support |

## Reporting a Vulnerability

Thank you for wanting to report a vulnerability. 
In the aim of transparency and encouraging collaborators to help resolve vulnerabilities in a timely manner we request all found vulnerabilities to be reported using the appropriate issue template within the Github Issues.
With one noteworthy exemption for zero-day exploits, which should be reported privately, as these require more specialized attention.

**Non zero-day vulnerabilities:**
Go to Issues -> choose the appropriate template -> share the vulnerability

**Zero-day vulnerabilities:**
Message *BallOf3lasticBands* privately

## After submitting a vulnerability report

A collaborator of the project will acknowledge your report within 3 working days (UTC).

After acknowledgment, we will assess the report and follow up with next steps. 
If the issue is confirmed, we will work on a fix and coordinate disclosure timing with the reporter when appropriate.

*Note that there is currently no bug bounty set. Your report will be met with gratefulness.*

## What not to do after finding a vulnerability

Unless discussed with a core collaborator or member of staff with expertise in cyber security, refrain from:

- Posting about unresolved vulnerabilities (social media, communication platforms, GitHub discussions, private websites, news and/or media, etc.)
- Using the found vulnerability to do harm to our collaborators, members of staff, supporters, clients, users, or otherwise acquainted (financially, physically, emotionally, or otherwise)
- Using the found vulnerability to demand a ransom in any way
- Do not include production secrets or private customer data in reports
- Do not perform destructive testing against shared hosted environments

Sharing your findings as a cyber researcher and getting the social credit for your work is an important right you have, however, please keep in mind the damage this can cause if done recklessly or before a fix can be rolled out.
